# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Create a Requester-facing ticketing application MVP that allows Requesters to create, view, and attach files to support tickets. We will use a temporary Development Requester selection to simulate user context before implementing real authentication in Lab 3.

## 2. Stakeholder Request Interpretation
The IT department needs an MVP ticketing system where end-users (Requesters) can submit IT support requests with categories, systems, priorities, and attachments. Requesters must be able to view their own tickets, filter them, and manage attachments. Since authentication is deferred to Lab 3, a mock "login" page is required for testing purposes to switch between seeded requester identities.

## 3. Scope
### Included
- Development Requester selection screen and context switching
- Create Ticket workflow with categorization and file attachments
- My Tickets list with search, filtering, sorting, and pagination
- Requester Ticket Detail view
- Attachment upload, download, and soft removal
- Requester ownership protection (cannot view others' tickets)
- Zen Green UI styling

### Excluded
- Real authentication, sessions, login/logout, and passwords
- IT Staff workflow (dashboard, claiming, reassigning, changing IT priority)
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken)
- Ticket lifecycle status changes beyond "New"
- Administrator functions (managing users, roles, reference data)

## 4. Functional Requirements
- FR-01 Development Requester Selection: The system must provide a screen to select from active seeded requesters. The selected requester becomes the owner of subsequently created tickets.
- FR-02 Ticket Creation: A requester can submit a ticket with a summary, description, category, related system, requested priority, and optional attachments.
- FR-03 My Tickets: A requester can view a paginated list of their own tickets, searchable by summary and filterable by category and status.
- FR-04 Ticket Detail: A requester can view details of their ticket, which are read-only except for attachment management.
- FR-05 Attachment Management: Requesters can upload up to 5 permitted files per ticket, download them, and soft-remove them (removing access but retaining metadata).
- FR-06 Ownership Protection: Requesters cannot access tickets or attachments belonging to other requesters.

## 5. Business Rules
- BR-01 The official Ticket Number is generated by the backend and must be unique (e.g., TKT-YYYY-XXXXXX).
- BR-02 A new Ticket begins with Current Status 'New'.
- BR-03 Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- BR-04 Inactive requesters must not appear in the Development Requester selector.
- BR-05 Ticket attachments are limited to JPG, PNG, WEBP, and PDF. Maximum size is 5MB per file. Maximum active attachments is 5 per Ticket.
- BR-06 Removed files are soft-removed; they must not be downloadable or previewed, but metadata remains visible.
- BR-07 Ticket summary and description are required. Category and Related System are required.
- BR-08 Ticket Summary must be between 5-100 characters. Description must be between 10-1000 characters.
- BR-09 The Create Ticket submit button must be disabled while a request is in progress to prevent duplicate submissions.
- BR-10 If ticket submission fails due to an API error, the form must retain all user-entered data and display an error message.
- BR-11 My Tickets list defaults to 10 items per page, sorted by `updatedAt` descending (newest first).
- BR-12 If a user has no tickets, display a clear "No tickets found" message with a prompt to create one. If a search yields no results, display "No matching tickets".
- BR-13 Uploaded filenames must be sanitized to prevent directory traversal or injection attacks.

## 6. UI Specification Summary
The UI will use the "Zen Green Theme". Required screens are App Shell, Requester Selection, Create Ticket, My Tickets, and Ticket Detail. See `ui-spec.md` for full details including color palette, form layout, and responsive requirements.

## 7. Data Changes
- **Models**: `RequesterUser`, `Ticket`, `Category`, `RelatedSystem`, `Attachment`.
- **Relationships**: A Requester has many Tickets. A Ticket belongs to one Requester. A Ticket has many Attachments. Categories and Related Systems are reference tables used by many Tickets.
- **Constraints/Fields**: 
  - `ticketNumber` (String, unique)
  - `currentStatus` (Enum/String, default 'New')
  - `isRemoved` (Boolean, default false) on Attachment

## 8. API Contract
See `api-spec.md` for full details.
- Endpoints cover fetching reference data (Categories, Systems), creating tickets, paginated fetching of owned tickets, fetching specific ticket details, and attachment lifecycle (upload, soft-remove, download).

## 9. Acceptance Criteria
- AC-01 Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (403 or 404).
- AC-04 Given the My Tickets screen, when the user changes pagination or filters, then the correct subset of their tickets is displayed.
- AC-05 Given an attachment over 5MB, when the user attempts upload, then the upload is rejected with a validation error.
- AC-06 Given a soft-removed attachment, when a user attempts to download it, then the API returns an error.
- AC-07 Given the Create Ticket form, when the user submits without a Summary or Description, then field-level validation errors appear immediately below the missing fields.
- AC-08 Given My Tickets is open, when the user changes the Development Requester, then the ticket list reloads to show only the new requester's tickets.
- AC-09 Given an owned ticket, when the user clicks remove on an attachment and provides a reason, then the attachment is soft-removed and can no longer be downloaded, but its metadata remains visible.
- AC-10 Given the My Tickets screen, when the user searches for a term with no matches, then the "No matching tickets" state is displayed.

## 10. Definition of Done
- Implementation of all approved scope.
- Satisfaction of all acceptance criteria.
- Passing and traceable automated tests (Unit, API, UI, E2E).
- Conformance to data, API, UI, validation, and responsive specs.
- Peer review and approval completed.

## 11. Assumptions and Decisions
- Assumption: The requester ID will be passed via a custom HTTP header (`X-Development-Requester-Id`) for backend APIs to simulate the logged-in user context.
